# Repositories and reviewed changes

Create a repository in the configured Cloudflare Artifacts namespace, or connect an existing repository in that namespace. Gitflare confirms its Artifacts remote and current branch head. For an empty repository or one with untouched Gitflare setup files, an Owner can import a ZIP as its first source commit. This does not import an arbitrary GitHub/GitLab URL or Git history, and matching a namespace name alone is not proof of external ownership.

ZIP import is available only before established source exists. It checks the current branch head again before writing, preserves setup files omitted from the ZIP, and requires repository Manage permission. Archives are limited to 5 MiB compressed, 500 files, 10 MiB expanded, and 1 MiB per file. Common secret, Git metadata, dependency, and build/cache paths are skipped; unsafe paths and special files are rejected. Review skipped entries and the exact base before committing. Existing source must be updated through Missions or the Artifacts Git workflow.

Live verification imported a ZIP into an empty repository through MCP and confirmed that exact-request replay returned the same commit. The imported tree included nested source/test files, binary assets, and an executable script, while `dummy.env` and `node_modules` were omitted. A separate initialized repository passed the UI selection, review, commit, and mission-navigation flow. After source was present, Gitflare correctly reported that ZIP import was no longer available. These results apply to those fixtures.

Browse a branch, tag, or commit before creating a Mission. Gitflare resolves refs to a commit SHA; use that immutable revision as the task base. A Mission is the current UI change record and execution attempt, containing the intended outcome, acceptance criteria, one to eight uniquely named assignments (two by default in combine mode), discussion, revisions, and execution evidence. The separate Proposal concept in the platform roadmap remains planned work. The form shows the target default branch and current HEAD. Creating a Mission saves a draft; starting it is a separate action that consumes Cloudflare and model resources. Combine mode is the default and merges assigned work for a shared check. Race mode requires at least two agents, each of whom attempts the whole Mission independently; a reviewer selects one passing candidate. Up to three agents run concurrently, with additional assignments waiting for a slot. These modes are implemented and covered by the 420-test source suite; final live race verification is pending. The workspace-wide **Missions** view and repository **Missions** view keep work grouped with its codebase.

The Mission form is available from **Create mission**. Existing deep links remain accepted at `/repository/<repository-id>/proposals/new` and the compatibility workspace route `/proposals/new`. It reads the current default-branch HEAD before submission and includes it as `expectedBaseSha`. A mismatch returns 409 and preserves the draft; refresh the base and review the new commit before submitting again. Start rechecks HEAD and pins execution to the commit current when the run begins. Live MCP `gitflare_proposal_base` returned the same branch and HEAD as the repository API. A stale base returned `STALE_PROPOSAL_BASE`, and a stale skill edit returned `STALE_SKILL_BASE`.

The repository has focused **Code**, **Issues**, **Proposals**, **Agents**, **Checks**, **Skills**, **Checkpoints**, and **Streams** views. Proposals are pull requests, Streams are Git branches, and Checkpoints are releases with their Git tags. Agents shows each task record, its assignment, run state, fork/stream, revision, changed files, and errors. Checks shows individual results and the combined candidate result with the SHA each one covers. Each task is designed to work in a separate fork and sandbox. Individual checks can pass while their combined candidate fails. File overlap is a signal for review, not proof of a semantic conflict.

The repository's **Skills** view discovers `SKILL.md` files beneath `.agents/skills/`, `.claude/skills/`, `skills/`, and `docs/skills/`. It resolves the selected branch, tag, or commit to an immutable SHA and previews instructions from that revision. Discovery is read-only: it does not install or execute a skill. The bounded scan reports truncation and skipped files so an incomplete result is visible.

The skill editor creates or updates `docs/skills/<lowercase-slug>/SKILL.md`. A create or update submits exact Markdown (up to 64 KiB, with `name` and `description` frontmatter) against an exact base commit from a principal with contribute and execute access. Gitflare queues one deterministic trusted-editor task, runs existing checks, and records a Mission; it makes no model call and does not write directly to the default branch. Live verification previously confirmed an MCP-created skill and a UI-edited skill each passed individual and combined checks, were approved, and landed. The newer mission-mode changes do not alter that skill evidence.

The **Cloudflare** project view lets an Owner search and filter the connected account catalog, select multiple Workers, D1 databases, Durable Object namespaces, Container applications, and Workflows, and label each with its environment. The current development project map contains seven resources: two Workers, three Durable Object namespaces, one Workflow, and one Container, all labeled `development`. The UI save, API read (HTTP 200), and MCP `get` returned identical records. Only the dedicated Gitflare runner was associated from the three Container applications in the catalog. Container usage counters are unavailable. D1 migration has not been exercised live.

Mission discussion is attached to the exact candidate SHA, base SHA, and execution epoch. Reviewers can comment or request changes; unresolved requests block approval and landing. Only the reviewer who raised a request can resolve it. Discussion is not an approval action and does not change source files.

Approve only the exact candidate and base SHAs shown in current evidence. Landing is separate and rechecks the approved candidate, passing checks, and canonical branch head before writing the tested commit. Landing does not deploy production. Cancelled or retried attempts retain distinct evidence; do not treat a queued state or agent summary as a passing result.

Preview uses a separate origin and an expiring capability tied to the candidate. A live preview opened successfully for a passing combined candidate and displayed that candidate's batch, concurrency, in-flight, and capacity values. This verifies one preview path; it does not establish compatibility for arbitrary applications or make the URL a public deployment.

The current execution policy is repository-configurable through a root `gitflare.json` committed at the pinned base. Candidate edits default to `src/`, `docs/`, `public/`, `static/`, `assets/` and `README.md`; existing tests, test configuration, package manifests, `.npmrc`, `.github/`, and the policy file itself remain protected (a starter repository's first mission may add `gitflare.json` once). `npm ci --ignore-scripts` is optional and package-registry access is limited to GET/HEAD while it runs. After install, the runner adds generated `node_modules/` to that worktree’s `.git/info/exclude`; shared repository ignore files are not changed, and tracked dependency edits remain blocked. The TAP evidence mode checks the full base-reported test set; `exit-code` mode trusts the command exit status and is labeled accordingly. This is not a general Git host or arbitrary-language build service. A live three-agent Mission completed three concurrent model-backed runs, passed all individual checks and the combined check, and landed at the approved candidate SHA. Each run loaded the same landed skill manifest with zero warnings; all three outputs included a marker specified by that skill and absent from the task prompts. A separate two-agent fixture passed the combined check, opened in a separate-origin preview, and landed at its exact approved commit. Another Mission passed its individual checks but failed its combined check and remained unlanded. The first four-agent race attempt failed because npm-generated untracked `node_modules/` entries were rejected as protected edits; no candidate was landed. A runner-local exclusion was added and the retry is pending. This does not establish successful live race or package-install execution. The completed fixtures remain limited evidence, not arbitrary-repository readiness or production deployment.

## Agent count, race missions and repository policy

A mission runs two to four agents in one of two modes. **Combine** gives each agent one part, shares each agent's assignment, notes and touched files with its peers, then merges and tests the parts together. **Race** has every agent attempt the whole mission; the passing candidates are shown side by side and a reviewer selects the one exact commit that can be approved and landed.

A repository may commit a root `gitflare.json` to set its test command, the paths agents may edit, an npm dependency install, a preview command, a test timeout of up to 900 seconds and a runner size. It is read from the pinned base commit and agents cannot change it, tests, manifests or lockfiles. Dependency install runs with network access limited to read-only requests to the npm registry and without package install scripts.

These capabilities are covered by automated tests. They have not yet been run end to end on Cloudflare; the live evidence above still describes a two-agent combine mission on the dependency-free fixture.

## Public repositories and handles

Every account can choose a **handle** in Account → Profile, and a workspace Owner can choose one for the workspace in Settings → General. A handle is 1–39 lowercase letters, numbers or single hyphens; names used by Gitflare's own pages (such as `api`, `docs`, `settings` or `repository`) are reserved. Choosing your account handle creates your personal workspace, which uses that handle. Renaming keeps the old address redirecting for 90 days, and nobody else can take the old handle during that time. A handle can change at most five times a day.

An Owner can make a repository **public** in its Settings → General. Gitflare asks for a `LICENSE` file on the default branch, or an explicit choice to publish without one, and records the change in the audit log. A public repository lives at `https://<site>/<handle>/<repository>`: anyone can read its code, commits, streams, releases and issues without signing in. Anyone signed in can open issues and comment there; proposals, missions, discussions, secrets, previews, deployments and settings stay private to the workspace.

**Issues on public repositories.** People outside the workspace open issues from the repository's templates (`.gitflare/ISSUE_TEMPLATE/*.md`, or `.github/ISSUE_TEMPLATE/*.md`), comment, edit what they wrote and report content to the Gitflare operator. Labels, assignees, closing, locking, hiding comments and blocking accounts belong to people who triage: the **Triager** role, Reviewers, Maintainers and Owners. Labels have colours and descriptions in Settings → Issues. A blocked account sees the repository's issues as not found. Outside accounts may post 10 times a minute; accounts younger than seven days may post 100 times a day and confirm they are human with Turnstile when the installation has it configured. Linked missions are never shown publicly. Making the repository private again takes effect immediately; copies people already cloned stay with them.

Anonymous reads go through one access check for a public principal that can only read a repository marked public in its own workspace. A private repository, an unknown repository and an unknown handle all return the same `404`. Commit lookups by SHA on the public pages are limited to the last 1,000 commits of the default branch. Anonymous requests are rate-limited per address. Old `/repository/<id>` links of a public repository lead signed-out visitors to its public address.

Anyone can clone or fetch a public repository over HTTPS without an account: `git clone https://<site>/<handle>/<repository>.git`. Pushing to that address asks for a personal token as the password (create one in Account → AI clients), and only workspace members with Contributor access can push, under the same stream protection as `/git/<repository>.git`. A private repository, an unknown one and an unknown handle all answer `Repository not found.`; clone a private repository with a token at `/git/<repository>.git` on the app host. SSH is not offered; use HTTPS with a token. Anonymous fetches are rate-limited per address, and `/llms.txt` lists recently published public repositories.

## Explore, search, stars and profiles

**Explore** (`/explore`) lists public repositories by stars, newest or recently updated, and by language. **Search** (`/search`) finds public repositories by name, description or handle, people by handle or display name, and files by **path**; file contents are not searched. Signed-in accounts can **star** and **watch** public repositories from the repository page; star counts are public and shape Explore. Every handle has a public **profile** at `https://<site>/<handle>` with a display name, bio, links, pinned repositories and its public repositories; a person's profile also lists the public repositories they starred. Edit your profile in Account → Profile and a workspace profile in Settings → General (Owner). Profiles show only what you enter there, never your account name or email.

Explore and search read a derived index that is updated when a repository becomes public or private, on every push and landing, on stars and on profile changes, and rebuilt nightly. Results are checked against the current public list before they are returned, so a repository that became private never appears, even before the index catches up. Anonymous public pages are cached at the edge for up to a minute and refreshed when the repository changes; signed-in requests are never served from that cache.
## Forks

Signed in, choose **Fork** on a public repository to copy its default branch into a workspace you own, usually your personal one. The fork is a private repository linked to its upstream; the upstream's page counts its forks. Push streams to the fork over HTTPS with a personal token created while that workspace is open (`git push https://<site>/<your-handle>/<repository>.git`). Nobody outside the upstream workspace can push to the upstream itself.

The fork's Code tab shows where it came from and whether its default branch is up to date. **Sync** moves the default branch forward to the upstream head; it never merges, so a fork whose default branch has its own commits must keep working on streams. Each fork holds up to 1 GiB. Gitflare counts the bytes pushed into a fork and synced from upstream, because Artifacts does not report a repository's size, and refuses a push or sync past the limit. Forking is rate-limited per account: 10 forks an hour and 5 of the same repository a day.

A private repository cannot be forked; it answers the same not-found as an unknown one. If an upstream is made private later, its forks keep their code but lose the link's address and sync.

Public repositories are part of hosted Gitflare; the self-hosted and demo editions keep every repository private.
